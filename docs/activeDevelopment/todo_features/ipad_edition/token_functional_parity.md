# Full original token functionality — required parity

**Status:** explicit user clarification, 2026-10-22. The original Tripling Season token object is deliberately designed; carry its entire functionality into the tablet product, fitting it into its lane. This is a requirement and review inventory, not a claim that a particular implementation currently fails or passes.

## Architectural correction

A new multiplayer container does not mean a new simplified token component. Reuse existing TokenCard and supporting implementation wherever practical. Adapt seat/session dependencies, lane constraints, history/persistence commands, player-facing keyboard and modal host. Preserve the tight density and direct interaction paths, not merely square-row aesthetics.

Separate ordered token/utility lanes and dedicated life regions remain accepted. Do not mount four unscoped ContentScreens or reuse unsafe global writes unchanged. Those integration constraints justify scoped adapters/refactoring, not deleting token capabilities. No arbitrary rebuild mandate remains.

## Integration changes versus regressions

Explicit new requirements govern integration: seat isolation and source-owned global modifiers; persistent chronological latest-action undo; all-modal whole-table blocking with dismissing gesture absorbed; no routine snackbar/toast; one initiating-player-facing custom keyboard; accepted art/preset/reset lifetimes. Preserve the token operation’s outcome and efficient access while adapting these boundaries. Existing partial-save bugs, unawaited writes or global storage collisions are not functionality to reproduce.

For any changed arrangement or behavior record: original operation, source/runtime evidence, proposed adaptation, concrete constraint, functionality/access preserved, exception approval if parity is reduced, and manual comparison evidence. “New UI,” “tablet,” or “cleaner component” alone is not sufficient justification. A transient prototype placeholder is not a release parity exception.

## Review and acceptance

Use Pass / Partial / Fail / Not implemented / Not tested for every inventory row, with separate source evidence and runtime steps/screenshots. Test compact and expanded views, long content, zero/one/many quantities, emblems, mixed counter types, custom/missing art, rule companions, same-name stacks and two seats with matching tokens. Include direct-control reachability and action count, not only visual resemblance. Verify old behavior against actual original implementation before alleging a mismatch.

No current runtime defect is asserted in this document. Independent implementation review findings belong in its evidence appendix; a missing first-pass feature is distinguished from a contradictory implemented behavior. Full parity is required for completed token implementation. Cloud visual/interactive inspection and small-tablet physical gates remain distinct.
