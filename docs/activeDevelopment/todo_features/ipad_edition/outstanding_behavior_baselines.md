# Outstanding behavior: old-design starting points

**Status:** inferred implementation/product starting points, not newly accepted user decisions. This second pass covers granular questions across the dossier, not only register headings. Read with the [source audit](existing_behavior_audit.md) and [accepted decisions](09_decision_register.md). Explicit tablet decisions, especially D41 modal dismissal and no routine toast/snackbar, override every legacy example.

## Concrete additional evidence

- **Wipes are not new games.** Current Set to 0 clears amount/tapped/sickness but retains counters and identity/art. Delete All clears tokens, not utilities; the third option also disables rules. The initial dialog has Cancel and named choices; snapshot precedes mutation and failures attempt rollback. This supports explicit operation previews and reversibility, not copying its field map into the accepted tablet resets. [Token mutations](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/providers/token_provider.dart#L1064-L1101), [choice, snapshot, rollback and completion](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/screens/content_screen.dart#L1006-L1131). Its non-dismissible completion is superseded; tapaway after commit does not undo.
- **Deck loading has two explicit existing workflows.** Clear-and-load deletes tokens, trackers and toggles; append starts after all existing kinds, preserves saved mixed order and does not merge matching tokens. Tokens start at zero; tracker values start at saved defaults and toggles OFF. Both reconstruct new runtime identities. Current sequential writes are not an atomic load. [Loader](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/providers/deck_provider.dart#L536-L624), [choices](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/screens/decks_list_screen.dart#L441-L459), [tracker template](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/models/tracker_widget_template.dart#L94-L114), [toggle template](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/models/toggle_widget_template.dart#L74-L90).
- **Recoverable writes already have a narrow precedent.** BoardOrderPersistence serializes order plans, flushes a validated journal before applying, flushes board boxes before deleting it and recovers before exposing providers. Reorder uses current state rather than stale positions. Extend that planning/recovery principle, not a claim all existing writes are atomic. [Order journal](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/services/board_order_persistence.dart#L11-L162). The old non-dismissible restart-only reorder failure dialog must be replaced with dismissible recovery context and a safe degraded state, not unlocked inconsistent data. [Failure UI](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/screens/content_screen.dart#L734-L763).
- **Preferences and presentation have usable defaults.** Current sickness display defaults on, art full-view, system theme on, experimental features off; Favorites use stable identities and Recent is deduplicated newest-first capped at 20. These are candidate app defaults, not permanent seat token-art preferences. Setters awaiting SharedPreferences do not establish robust failure rollback. [Settings](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/providers/settings_provider.dart#L37-L106). Existing token semantics label expansion, counts and edit/art/counter actions, which is a baseline, not proof rotated keyboard accessibility works. [Token semantics](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/widgets/token_card.dart#L264-L272), [count semantics](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/widgets/token_card.dart#L486-L492), [inline edit semantics](https://github.com/didymusbenson/Doubling-Season/blob/d30050bd7a1067058fcdf7e707d3a223124a79fb/lib/widgets/inline_token_edit_field.dart#L39-L46).

## Baseline map for remaining questions

Every “start with” below is an inference for design/prototyping, not an approved release promise. Where no precedent can answer the new question, the gap is stated explicitly. Accepted behaviors are not reopened.

| Question / dependent decisions | Existing-design answer or concrete starting point | What still cannot be inherited |
|---|---|---|
| Search dismissal, nested quantity, unfinished creation (D10/D11) | Transient search; nested cancel returns to parent query; explicit Create. Preserve Recents/cache side effects but no unsubmitted board addition. | Safe completion of an already submitted async command after dismissal requires scoped command identity/recovery, not a new preference question. |
| Rename and customization (D19) | Existing token fields commit on exit; existing deck valid names save live; new-object naming submits explicitly. Start seat-name editing with existing-object live valid edits and persistent life-art selection with explicit selection. | Seat-name validation/empty-name policy is not proved by deck validation; do not apply token empty-text permission universally. |
| Inline counters and life adjustments (D16/D26) | Live ±, staged typed Set, clear labels distinguishing delta from replacement. Start larger-step controls from existing configurable tracker steps, not arbitrary token quantity limits. | Exact life bounds/step presets, grouped settlement display and corrections require field-specific design; accepted approximate 1–2 second life window is not an exact timer. |
| Status and commander controls (D26) | Start from explicit toggles/manual numeric edits; preserve separate source and recipient labels and independent corrections. | Old generic toggles cannot define shared monarch exclusivity, three-state day/night or partner-source identity. Accepted shared/coupled contracts supply those, not copied utility storage. |
| Wipe targets and confirmation (D22/D36) | Start with a central named-operation chooser, affected-seat selection and explicit Apply/Cancel; preview what will clear. This adapts old named wipe choices without silently choosing a seat. | Which targets are offered/defaulted and exact wipe field map remain product design. Do not assume central means all seats, or count-zero equals reset-with-board. |
| Full resets and utility defaults (D22/D37) | Accepted reset matrix wins. Use saved tracker defaults/toggle OFF as a candidate per-kind reset mapping; clear gameplay mana/storm while retaining configured utility kinds in keep-board. | Confirm the utility/rule field map, especially nonzero reusable defaults and enabled rule configuration; old token-only wipe does not decide this. |
| Undo presentation and grouping (D16) | Start with visible Undo in game history, explicit committed operation feedback in context, and before/after records; no snackbar dependency. Group only compatible consecutive actions; keep constituent commands. | Old one-shot board-wipe snapshot cannot decide undone-row presentation, redo inclusion or exact timeout. Conservative starting point: mark undone rows rather than lose audit context; redo is not a commitment. |
| Navigation and non-gameplay history (D16/D37) | Start by logging gameplay changes, not opening a menu; preserve settings/order separately. Conservatively settle a pending gameplay group before changing edit context so no later action rewrites earlier chronology. | Whether presentation edits appear in/consume game undo remains unresolved; this inferred grouping boundary is not a user-confirmed rule about every navigation event. |
| Archive restore and current game (D33) | Start with explicit archive selection and a preview of historical seats/configuration. Proposed preservation of the current game before replacement remains a safeguard proposal. | Old app has no durable game archive; retention, browsing, restore/customization conflicts and preservation approval remain genuinely new. Never silently treat old immediate Undo as archive recovery. |
| Preset setup loading (D38) | Existing replacement workflow plus zero-state templates is a strong starting point for setup-time seat load. Reconstruct distinct runtime IDs, utilities at configured defaults and OFF toggles, with optional explicit life-art application. | Dedicated life and shared statuses cannot be duplicated from generic legacy utilities. Commander inclusion is not accepted. |
| Midgame presets (D38) | Offer clearly separated Replace seat setup and Add setup as candidate workflows, based on old clear/add choices; append after existing entries without automatic merge. Preview replacement and make any committed load one coherent operation. | Availability, life effects, exact merge/replace semantics, confirmation and history handling are still product choices. Existing no-extra-confirmation/sequential writes are not approved safety behavior. |
| Utility hide, restore and defaults (D37) | Accepted confirmed hide preserves values; restore via menu. Start from saved utility configuration/defaults and existing catalog kinds, with storm/mana default visible. Show hidden nonzero state in the menu rather than a toast. | Exact curated inventory, hidden-value indicator design and reset provisioning need mapping, not arbitrary user-authored widgets or free panel resizing. |
| Mana and consumption shortcuts (D27) | Start with manual typed/color counters and explicit clear controls, matching existing manual tracker philosophy. | Automatic spending, phase/turn emptying, restrictions and Treasure-to-mana coupling have no established equivalent and are not implied. Prototype/manual baseline does not approve these mechanics. |
| Dice/shared tools (D28) | Start with explicitly invoked tools whose result is shown in the open panel; no automatic game mutation or toast. | Dice kinds, history inclusion, timers and other tools need a bounded inventory; research icons are not requirements. |
| Ordering and grouping (D13) | Append ordinary entries, source-adjacent copies/splits, stable manual drag order; preserve exact-art/clean-counter merge rules per route. Apply independently to each seat/lane. | Splitting mixed saved preset order into dedicated token/utility lanes needs stable within-kind ordering; do not merge merely by name or silently resort after count/art edits. |
| Expansion/collapse (D10) | Start with existing collapse-first then fresh tap, and one expanded nonmodal item per seat as a multi-seat adaptation; every modal still blocks all seats. | Per-seat expansion is an inferred prototype baseline, not evidence old single-board code supports it. Measure capacity before changing behavior. |
| Library sorting versus board sorting (D13/D20) | Preserve user board order separately from catalog search ranking and Recent/Favorites. Start library views from existing sort/filter controls. | Cross-seat library sharing and profile-level favorites policy are not settled by current globals. Token-art preferences remain current-game/seat scoped regardless. |
| Artwork selection/caching/missing assets (D20/D39) | Preserve selected metadata, try cache/remote fallback, keep usable placeholder and explicit retry/reselect. A missing file must not reset a choice. Art readiness should not prevent unrelated controls being usable. | Custom asset IDs/retention and web offline guarantees require technical work; current mutable file references and unawaited saves are limitations, not defaults. |
| Token shape and display (D07/D08) | Content-driven square rows, identity rail, readable art backdrop, zero-state dimming, complete counter access and inline editing. | Exact tablet dimensions, overflow capacity and editor mapping need visual/interactive evidence; generated C styling is not a specification. |
| Persistence and command architecture (D14/D15/D17) | Extend journal-before-apply/recover-before-expose design to scoped state+history commands; one session writer is a concrete starting architecture. Use current revisions and idempotent IDs. | Existing order-only journal does not prove arbitrary multi-box atomicity. Choose aggregate/journal/records based on recovery tests; no user preference question is required to design this safely. |
| Save failure and startup recovery (D17/D31) | Preserve last acknowledged state and recoverable draft/plan; show persistent inline recovery context and explicit retry. Block unsafe mutations without trapping a modal. | Legacy catches, partial saves or destructive fresh-box fallback cannot satisfy durable game/history guarantees. Never silently erase/reseed a game to make startup succeed. |
| App versus seat preferences (D19) | Start theme/accessibility/catalog display at app scope; persistent names/life appearance at seat scope; utility setup and token art at accepted game/preset scope. | Old global stores cannot settle all preference scoping. Any shared favorites/library changes must not mutate another seat’s selected art. |
| Accessibility (D12) | Preserve named actions/counts/edit semantics, explicit buttons for gesture-only actions and text-scaling layouts; prototype rotated focus order and hardware operation. | No existing evidence proves arbitrary-seat screen-reader traversal or custom IME composition. Failures need design alternatives, not a claim pixel rotation is enough. |
| Custom keyboard extras (D11) | Start numeric fields with plain validated numbers and text fields with existing plain text; add no symbol encoding to existing export/search by accident. | Old native inputs cannot settle custom grapheme/selection/IME/localization. Canonical symbol tokens plus readable fallback are a candidate, not accepted syntax or first-release feature. |
| Layout/window/device floor (D05/D06/D30) | Start at accepted 2/3/4 layouts and existing content-driven rows; test target windows and long boards before picking dimensions. Focused-seat fallback is a candidate only if measurement demands it. | Portrait phone behavior cannot establish tablet minimums, four-seat orientations or a fallback product promise. Physical tablet, Android and web evidence remain distinct gates. |
| Feature parity and shared effects (D08/D25) | **Updated by explicit decision:** each seat owns local/global modifier sources; global sources affect the table. Retain calculator semantics through an applicable-source projection rather than copied mutable toggles. | Source-label/Other effects presentation is recommended, not mandated. Validate ordering, independent copies and deduplication; reset activation mapping and token transfers remain unresolved. |
| Migration/export/interoperability (D18/D23/D29/D34) | Start with explicit reusable deck import, preview omissions, no silent live-board assignment and independent product storage. Preserve source files and existing v3 interpretation. | Legacy live-game import, shared live storage, new export format/subsets and privacy/retention promises need scope choices; custom art reference transport needs technical design. |
| Offline/update/release/business (D02/D03/D31/D32) | Existing local state and cached art support a local-first prototype; allow honest missing-art fallback. Keep migration/recovery safe across versions. | New product name, pricing, rollout order, supported browsers and formal offline/update guarantees have no old-design answer. These are product/release decisions, not reasons to block the current interaction prototype. |
| Six-player expansion | Keep stable seat IDs, source IDs and layout strategies extensible; existing content-driven lists avoid fixed four-seat storage assumptions. | Six-seat usability and extra geometry are deferred, not requirements to implement now or evidence to add one-player scope. |

## Next consequential unknown

**Next: midgame preset loading (D38).** Setup-time zero-state load is accepted. The old app offers clear-and-load and append, but the tablet still needs to decide whether midgame loading is available as replace, append or both, and how it affects existing gameplay values, life and the undo timeline. Start from those explicit old workflows and a visible affected-seat preview, not an implicit full reset. This is the next product question after the accepted modifier-scope decision.

**Following that:** measured minimum-window/fallback support (D06/D30). D25 is no longer an open local-only-versus-global question: source-owned global applicability is accepted. Token-control transfers remain separate, not bundled into that answer. Many other remaining details have concrete prototype defaults; no numeric “questions closed” total is claimed because register rows mix accepted categories, inferences and technical subquestions.

## Validation obligations for these inferences

Compare setup load versus append with mixed utilities, zero-state tokens and independent seat art; exercise each wipe choice separately from full reset; interrupt journaled writes and recover coherently; verify all-modal tapaway even after failures without unlocking unsafe state; test counts/labels and keyboard traversal at rotated seats. Check local versus shared rule applicability explicitly before any first-release parity claim. These are planned manual cases, not tests reported as passed.
